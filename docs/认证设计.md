## 一、三条登录路径

```
                        ┌──────────────────────────┐
   主路径（不依赖外部服务）│  用户名 / 邮箱 + 密码      │  ← 演示、日常都用这条
                        └────────────┬─────────────┘
                                     │
   ┌─────────────────────────────────┼─────────────────────────────────┐
   │                                 │                                 │
   ▼                                 ▼                                 ▼
备选：邮箱 + 验证码            找回密码：邮箱 + 验证码            （未来）手机验证码
（收得到信就能登）             → 设置新密码
```

**为什么这么分**：登录是所有演示的第一个动作。把邮箱放在**必经路径**上，一旦邮件延迟或
服务抖动，演示就卡在第一屏。所以：

- **密码登录不碰任何外部服务** —— 一定能用
- 验证码登录和找回密码都是**可选的增强路径**
- 发信失败**不影响接口成功返回**

## 二、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/auth/register` | 注册：`username` + `email` + `password`，可选 `role` |
| POST | `/api/auth/login` | 密码登录，`account` 可以是**用户名或邮箱** |
| POST | `/api/auth/code/send` | 发验证码，`purpose` = `login` \| `reset_password` |
| POST | `/api/auth/code/login` | 验证码登录 |
| POST | `/api/auth/password/reset` | 重置密码 |
| GET | `/api/auth/me` | 当前用户（未登录返回 401） |
| POST | `/api/auth/logout` | 退出 |
| POST | `/api/auth/mail/test` | 发测试邮件（需登录，部署自检用） |

统一响应格式：

```json
{"ok": true,  "data": {...}}
{"ok": false, "error": "人类可读的原因"}
```

**示例**

```bash
# 注册
curl -X POST https://xllm.cloud/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","email":"alice@example.com","password":"Passw0rd!","role":"customer"}'

# 登录（用户名或邮箱都行）
curl -X POST https://xllm.cloud/api/auth/login -c cookie.txt \
  -H 'Content-Type: application/json' \
  -d '{"account":"alice","password":"Passw0rd!"}'

# 用 cookie 访问需要登录的接口
curl https://xllm.cloud/api/auth/me -b cookie.txt
```

## 三、验证码的六条规则

| 规则 | 实现 | 为什么 |
|---|---|---|
| **5 分钟过期** | `email_codes.expires_at` | 有效期过长等于没有 |
| **一次性** | 用后写 `used_at` | 防重放 |
| **60 秒限频** | 查最近一条 `created_at` | 防刷爆邮件额度 |
| **每小时 5 条上限** | 按 `created_at > now-1h` 计数 | 同上 |
| **错误 5 次作废** | `attempts` 递增 | 6 位码可被暴力枚举 |
| **只存哈希** | `werkzeug.generate_password_hash` | 库泄露不等于验证码泄露 |

另外：**新码下发时旧码立即作废**，避免同时存在多个有效码。

## 四、几个安全决策

### 1. 不泄露「这个账号存不存在」

两处都做了处理：

- **登录失败**：用户不存在和密码错误返回**同一条**信息 `账号或密码不正确`
- **发送验证码**：无论邮箱是否注册，对外返回**完全一致**的响应

否则攻击者可以拿登录接口当"账号探测器"。

### 2. 密码只存哈希

```python
user.set_password(raw)      # werkzeug scrypt，自带随机盐
user.check_password(raw)    # 恒定时间比较
```

同一密码每次哈希结果都不同，`password_hash` 永远不会出现在任何 API 响应里（`to_dict()` 里没有它）。

### 3. 会话

- Flask session（服务端签名的 cookie），与 week-5 讲的方式一致
- `login_user()` 会先 `session.clear()` —— **防会话固定攻击**
- 线上 `SESSION_COOKIE_SECURE=1`，cookie 只走 HTTPS
- `HttpOnly` + `SameSite=Lax`

### 4. 权限装饰器

```python
@require_role("rider")
def accept_order(): ...
```

⚠️ 但要注意：`require_role` 只解决"这个**角色**能不能调这个接口"。
**数据级归属**（骑手只能看自己的单）必须在每个查询里再写一次：

```python
order = Order.query.filter_by(id=oid, rider_id=current_user().id).first_or_404()
```

## 五、开发与运维

### 调试时不怕邮件延迟

`DEBUG=1` 时，`/api/auth/code/send` 会把验证码**直接回显**在响应里：

```json
{"ok": true, "data": {"expires_in": 300, "debug_code": "193951", "sent": true}}
```

线上（`debug=False`）不会出现 `debug_code`，也不会出现 `sent`（后者会泄露邮箱是否注册）。

### 看发信日志

```bash
ssh xllm 'sudo journalctl -u xllm -f | grep "\[mail\]"'
```

```
[mail] 已发送 → someone@example.com | xLLM · Sign-in code: 193951
[mail] 发送失败 → xxx@yyy.com | ... | SMTPAuthenticationError: ...
```

⚠️ Flask 默认只在 debug 模式下打 INFO 日志，`app.py` 里显式设了
`app.logger.setLevel(logging.INFO)`，否则"发送成功"是一条都看不到的（这个坑踩过）。

### 发件人配置（2026-10 · 自动发信统一走 no-reply）

| 项 | 值 | 说明 |
|---|---|---|
| `MAIL_USER` | `no-reply@xllm.cloud` | SMTP 认证账号（凭据已有，已验证可用） |
| `MAIL_SENDER` | 与 `MAIL_USER` 相同 | 对外发件地址 |
| `MAIL_SENDER_NAME` | `xLLM Food Delivery` | 英文显示名；置空则只显示地址 |
| `MAIL_REPLY_TO` | `contact@xllm.cloud` | 用户点"回复"落到的信箱；置空则不加该头 |
| `MAIL_PASSWORD` | no-reply@ 的客户端授权码 | 只放服务器 `.env` |

收件人看到的完整身份：

```
From:     xLLM Food Delivery <no-reply@xllm.cloud>
Reply-To: contact@xllm.cloud
```

**为什么自动发信用 `no-reply@` 而不是 `contact@`：**

1. `noreply` 的语义就是"只出不进"——系统自动发的邮件不该落进某个人的收件箱等人处理。
2. 发件地址**必须等于 SMTP 认证账号**（企业邮校验 `From`）。用 `contact@` 发就得额外拿到
   contact@ 的授权码，而这一步完全可以避免。
3. "用户要能回复"的需求由 `Reply-To` 满足。它只是邮件头字段，**不需要** contact@ 的任何凭据。

**`contact@` 的正确用途**：收回复、合作咨询、对外联系方式 —— 只收不发。

🔴 **硬约束（保留）**：腾讯企业邮用"实际登录的账号"校验 `From`。若 `MAIL_SENDER` 与
`MAIL_USER` 不是同一个账号，发信会被拒绝（553）或被改写回登录账号。
`mailer.py` 在两者不一致时会打 WARNING 日志，便于定位。

⚠️ **`.env` 写法**：`MAIL_SENDER_NAME` 含空格，必须加引号。

```bash
MAIL_USER=no-reply@xllm.cloud
MAIL_SENDER_NAME="xLLM Food Delivery"      # 不加引号会让 source .env 报 Delivery: command not found
MAIL_REPLY_TO=contact@xllm.cloud
```

（systemd 的 `EnvironmentFile` 能容忍不加引号，但任何 `source .env` 的脚本会炸——
线上原来的 `MAIL_SENDER_NAME=xLLM 外卖` 就有这个问题。）

### 邮件正文已全部英文

与 UI 语言一致。验证码邮件示例：

```
Subject: xLLM · Sign-in code: 193951

Here is your sign-in code for xLLM:

        193951

The code expires in 5 minutes and can be used only once.
Requesting a new code invalidates the previous one.

If you did not request this, you can safely ignore this email — your account is unchanged.

— xLLM Food Delivery (course project; automated message, please do not reply)
```

### 部署自检

登录后调 `POST /api/auth/mail/test`，`data.sent` 为 `true` 即邮件通道正常。

## 六、三端登录页

凭据是同一套，界面是三个：

| 端 | 页面 | 样式 | 登录后跳转 |
|---|---|---|---|
| 顾客 | `/customer/login` | 白底红胶囊，含验证码登录 / 忘记密码 | `/customer/` |
| 商家 | `/merchant/login` | 左侧品牌渐变 + 右侧表单 | `/merchant/`（没开店 → `/merchant/setup`） |
| 骑手 | `/rider/login` | 浅灰底、56px 橙色大按钮 | `/rider/` |

角色校验在服务端：`@require_role` 管接口、`@role_page` 管页面。
在顾客端登录页登录商家账号不会被"误放"进商家界面 —— 页面守卫会按 `user.role` 判断，
接口也会返回 403。三端登录页互相链接，方便评委切换。

## 七、测试结果

2026-10-22 对公网 `https://xllm.cloud` 跑完整端到端测试（含**真实发信 + IMAP 取码**）：

```
注册 / 会话 / 密码登录 / 验证码登录 / 找密码 / 限频 / 邮件自检
结果: 21 通过 / 0 失败
```

覆盖的场景：

- 注册返回 201，响应不含 `password_hash`
- 登出后 `/me` 返回 401
- 错误密码、不存在的用户都返回 401（信息一致）
- 用户名登录 ✓ / 邮箱登录 ✓
- 验证码：发送 200 → 紧接着重复发送 429 → 错误码 400 → 正确码 200 → 同码复用失败
- 找回密码：重置后旧密码 401、新密码 200
