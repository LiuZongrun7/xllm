```
用户浏览器
    │  https://xllm.cloud
    ▼
┌─────────────────────────────────────────┐
│  nginx  (:443, TLS)                     │
│    /            → 静态文件               │

    │  http (仅本机回环)

│    └── Flask  app:app                   │

```

**要点：gunicorn 只绑 `127.0.0.1`，不对外。** 外部流量一律经 nginx，
这样才能保证 HTTPS、统一入口、以及将来加限流/日志。

## 三、nginx 转发规则（⚠️ 已修订）

**先纠正一个原来的错误假设**：旧版这里写的是"`/` 走静态文件"，但三端页面是 **Jinja2 模板**，
必须由 Flask 渲染。如果 `/` 仍由 nginx 直接发静态文件，访问 `/customer/...` 会 404。

**现在的规则：`/` 与 `/api/` 都转给 gunicorn。**

```nginx
# 页面 + 静态资源 + 接口，全部交给 Flask
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# 显式保留 /api/（更具体的 location 优先），语义更清楚
location /api/ {
    proxy_pass http://127.0.0.1:8080;   # ← 结尾【不带】斜杠 = 保留原路径
}
```

为什么 `/api/` 仍要单独写一条：`proxy_pass` 结尾**带**斜杠会剥掉 `/api` 前缀，
导致 `url_for()` 生成的地址和浏览器实际访问的地址不一致。

```python
url_for("health.ping")   # 带斜杠 → 生成 "/ping"，但浏览器要访问 "/api/ping" ❌
                         # 不带斜杠 → 生成 "/api/ping" ✅
```

保留前缀后，`url_for` 在 Jinja 模板里可以直接用，不会踩坑。

### 静态资源为什么也走 Flask

三个端各自的静态资源在各自的蓝图下（`/customer/static/...`、`/merchant/static/...`、
`/rider/static/...`），这样"删掉一个端的目录就等于删掉这个端"。
让 nginx 逐条 alias 反而要维护三份重复配置，和隔离的初衷相悖。

课程项目规模（3 个 worker、几个 CSS/JS 文件）下 Flask 直接发静态资源完全够用。
若将来要优化，再加一条 `location /customer/static/ { alias /home/ubuntu/xllm/server/customer/static/; }`
并把缓存头加上即可 —— 属于优化，不是必需。

### 写法约定

公共接口挂在 `shared/` 下，`url_prefix="/api"`；三端各自的接口挂在**各自的目录**里，前缀 `/api/<角色>`：

```python
# shared/health.py —— 公共
bp = Blueprint("health", __name__, url_prefix="/api")

@bp.get("/ping")           # → 实际路径 /api/ping
def ping(): ...

# customer/routes.py —— 顾客端自己的接口
api = Blueprint("customer_api", __name__, url_prefix="/api/customer")

@api.get("/orders")        # → 实际路径 /api/customer/orders
def my_orders(): ...
```

**不要在单个路由里手写 `/api` 前缀**，前缀统一由 Blueprint 提供。

### 本地开发时的差异

本地没有 nginx，直接访问 Flask 原始路径，**仍然带 `/api`**：

```
https://xllm.cloud/api/ping     ← 线上
http://127.0.0.1:8080/api/ping  ← 本地
```

两边路径现在完全一致了，这是方案 A 的另一个好处。

## 五、修改代码后的部署流程

### 5.1 单文件小改

```bash
scp server/app.py xllm:~/xllm/app.py
ssh xllm 'cd ~/xllm && .venv/bin/pip install -r requirements.txt'   # 仅当依赖变了
ssh xllm 'sudo systemctl restart xllm'
curl -s https://xllm.cloud/api/ping
```

### 5.2 整目录同步（2026-10-22 实测流程）

```bash
# 1. 先备份代码与配置（不含 .venv，那个太大且不需要备份）
ssh xllm 'cd /home/ubuntu && tar czf xllm-backup-$(date +%Y%m%d-%H%M%S).tar.gz \
          --exclude=.venv --exclude=__pycache__ xllm'
ssh xllm 'sudo cp /etc/nginx/sites-available/xllm.cloud ~/nginx-xllm.cloud.bak'
ssh xllm 'cp /home/ubuntu/xllm/.env /home/ubuntu/xllm/.env.bak'

# 2. 同步（⚠️ 不要加 --delete，见下方红线）
rsync -az \
  --exclude='__pycache__' --exclude='.env' --exclude='.venv' \
  server/ xllm:/home/ubuntu/xllm/

# 3. 删除已被淘汰的旧文件（rsync 不会替你删）
ssh xllm 'cd /home/ubuntu/xllm && rm -rf blueprints extensions.py mailer.py \
          models.py security.py utils.py __pycache__'

# 4. 重启并验证
ssh xllm 'sudo systemctl restart xllm && systemctl is-active xllm'
curl -s -o /dev/null -w '%{http_code}\n' https://xllm.cloud/customer/design-system
```

### 🔴 红线：`rsync --delete` 不能指向项目根目录

2026-10-22 实际踩过：对 `xllm:/home/ubuntu/xllm/` 执行 `rsync --delete`，
它把 **`.venv/` 删掉了**（`.venv` 不在本地 `server/` 里，于是被判定为"多余文件"）。
服务当时看着还 `active`（gunicorn 进程还在内存里），但一旦重启就会 `No such file` 起不来。

恢复办法（无需备份，直接重建）：

```bash
ssh xllm 'cd /home/ubuntu/xllm && rm -rf .venv && python3 -m venv .venv \
          && .venv/bin/pip install -q -r requirements.txt'
```

**结论**：要么不加 `--delete`（推荐，旧文件手动删），要么把 `.venv` 和 `.env`
显式写进 `--exclude`。当前流程取前者。

### 5.3 回滚

```bash
ssh xllm 'cd /home/ubuntu && rm -rf xllm && tar xzf xllm-backup-<时间戳>.tar.gz'
ssh xllm 'sudo cp ~/nginx-xllm.cloud.bak /etc/nginx/sites-available/xllm.cloud'
ssh xllm 'sudo nginx -t && sudo nginx -s reload && sudo systemctl restart xllm'
```

> 💡 建议：等 M2 阶段搭好 Git 仓库后，把 5.2 写成一个 `deploy.sh`，
> 或者用 GitHub Actions 自动部署。目前**没有版本控制**，备份 tar 就是唯一的回滚手段。

## 六、🔒 密钥管理规则

**服务器上目前有三类凭证，规则完全不同：**

| 凭证 | 放哪 | 能否进 Git | 保护方式 |
|---|---|---|---|
| 高德 **Web端** Key<br>`2c60b2cd...` | 前端 HTML/JS | ✅ 可以 | 高德控制台的**域名白名单** |
| 高德 **安全密钥**<br>`59b46489...` | 前端（JS API 2.0 要求） | ⚠️ 见下 | 正式环境应改为后端代理 |
| 高德 **Web服务** Key<br>`1a2a76ac...` | **只能后端** | ❌ **绝对禁止** | 环境变量 |
| MySQL 密码 | 后端 `.env` | ❌ **绝对禁止** | 文件权限 600 |

**Web端 Key 是设计上公开的**——它必然随页面下发，任何人 F12 都能看到。
所以它的安全**不靠保密，靠域名白名单**。请务必在高德控制台配好：

```
应用管理 → 我的应用 → 设置 → 域名白名单
xllm.cloud
www.xllm.cloud
127.0.0.1
localhost
```

**Web服务 Key 和数据库密码是真机密**，只能存在于服务器端：

```bash
# 建议做法：放在 ~/xllm/.env，权限 600，且 .env 已进 .gitignore
chmod 600 ~/xllm/.env
```

> ⚠️ 仓库根目录的 `.gitignore` 已经屏蔽了 `.env`、`*.pem`、`*.key`、
> `*credentials*.txt`。**提交前请再确认一遍**，密钥一旦进了 Git 历史，
> 即使后来删掉也仍然能被翻出来。

## 七、本地开发

```bash
cd server
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python app.py                      # http://127.0.0.1:8080
```

本地跑时**没有 nginx**，直接访问 Flask。由于方案 A 保留了前缀，
**本地和线上路径完全一致**：

```
https://xllm.cloud/api/ping      ← 线上
http://127.0.0.1:8080/api/ping   ← 本地
```

本地还需要一份 `.env`（数据库密码等）。**不要提交它**，`.gitignore` 已经屏蔽：

```bash
# server/.env
SECRET_KEY=本地随便填一个
DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=webapp
DB_USER=webapp
DB_PASSWORD=你的密码
```

Flask 不会自动读 `.env`（本项目没装 python-dotenv，保持依赖精简）。
本地开发时用 export 或者命令行前缀：

```bash
export $(grep -v '^#' .env | xargs)   # 简单粗暴地导入
python app.py
```
