## 三、nginx 转发规则（⚠️ 已修订）

**先纠正一个原来的错误假设**：旧版这里写的是"`/` 走静态文件"，但三端页面是 **Jinja2 模板**，
必须由 Flask 渲染。如果 `/` 仍由 nginx 直接发静态文件，访问 `/customer/...` 会 404。

**现在的规则：`/` 与 `/api/` 都转给 gunicorn。**

```nginx
# 页面 + 静态资源 + 接口，全部交给 Flask
location / {
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# 显式保留 /api/（更具体的 location 优先），语义更清楚
location /api/ {
    proxy_pass http://127.0.0.1:8080;   # ← 结尾【不带】斜杠 = 保留原路径
}
```

为什么 `/api/` 仍要单独写一条：`proxy_pass` 结尾**带**斜杠会剥掉 `/api` 前缀，
导致 `url_for()` 生成的地址和浏览器实际访问的地址不一致。

```python
url_for("health.ping")   # 带斜杠 → 生成 "/ping"，但浏览器要访问 "/api/ping" ❌
                         # 不带斜杠 → 生成 "/api/ping" ✅
```

保留前缀后，`url_for` 在 Jinja 模板里可以直接用，不会踩坑。

### 静态资源为什么也走 Flask

三个端各自的静态资源在各自的蓝图下（`/customer/static/...`、`/merchant/static/...`、
`/rider/static/...`），这样"删掉一个端的目录就等于删掉这个端"。
让 nginx 逐条 alias 反而要维护三份重复配置，和隔离的初衷相悖。

课程项目规模（3 个 worker、几个 CSS/JS 文件）下 Flask 直接发静态资源完全够用。
若将来要优化，再加一条 `location /customer/static/ { alias /home/ubuntu/xllm/server/customer/static/; }`
并把缓存头加上即可 —— 属于优化，不是必需。

### 根路径 `/` 与官网 `/info/`

官网是 Flask 里一个独立的蓝图（`server/info/`），它不读数据库、不需要登录。
`/` 只是一个 302：

```python
@app.get("/")
def root():
    return redirect(url_for("info.index"))     # → /info/
```

**nginx 不需要为它改任何东西** —— 因为 `location /` 本来就整段转给 gunicorn，
`/info/`、`/info/static/...` 和 `/customer/...` 走的是同一条规则。
用 302 而不是 301，是因为这站还要改；301 会被浏览器长期缓存，改回来很麻烦。

```bash
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' https://xllm.cloud/
# 302 https://xllm.cloud/info/
```

### 写法约定

公共接口挂在 `shared/` 下，`url_prefix="/api"`；三端各自的接口挂在**各自的目录**里，前缀 `/api/<角色>`：

```python
# shared/health.py —— 公共
bp = Blueprint("health", __name__, url_prefix="/api")

@bp.get("/ping")           # → 实际路径 /api/ping
def ping(): ...

# customer/routes.py —— 顾客端自己的接口
api = Blueprint("customer_api", __name__, url_prefix="/api/customer")

@api.get("/orders")        # → 实际路径 /api/customer/orders
def my_orders(): ...
```

**不要在单个路由里手写 `/api` 前缀**，前缀统一由 Blueprint 提供。

### 本地开发时的差异

本地没有 nginx，直接访问 Flask 原始路径，**仍然带 `/api`**：

```
https://xllm.cloud/api/ping     ← 线上
http://127.0.0.1:8080/api/ping  ← 本地
```

两边路径现在完全一致了，这是方案 A 的另一个好处。

### 三个子域名与证书（2026-10 追加）

三个端现在各有一个独立域名，答辩时 URL 栏里就能看出来是三个站：

| 域名 | 落到的端 | 证书 |
|---|---|---|
| `customer.xllm.cloud` | 顾客端 `/customer/` | 单域名 DV（TrustAsia，三个月） |
| `restaurant.xllm.cloud` | 商家端 `/merchant/` | 同上 |
| `delivery.xllm.cloud` | 骑手端 `/rider/` | 同上 |
| `xllm.cloud` | 官网 `/info/` + 管理大屏 `/admin/` | 原有的那张（含 `www`） |

**分工：nginx 管收，Flask 管分。**

nginx 只做它擅长的三件事：绑证书、收 TLS、转给 gunicorn。四个域名最终都指向同一个
`127.0.0.1:8080`，配置在 `deploy/nginx/xllm-subdomains.conf`（三个 `server` 块，
内容一样，只有 `server_name` 和证书不同 —— 因为证书是单域名的，不能共用）。

"哪个域名该落在哪个端"由 `server/shared/hosts.py` 的一个 `before_request` 决定：

```
customer.xllm.cloud/            → 302 /customer/            根路径落到本端首页
customer.xllm.cloud/merchant/x  → 302 restaurant.xllm.cloud/merchant/x   跨端跳域名
delivery.xllm.cloud/info/       → 302 xllm.cloud/info/      官网只留在主域名
customer.xllm.cloud/api/...     → 不干预                     接口不分域名
```

最后一条是有意为之：接口如果也按域名 302，`fetch` 就会被跳到另一个 origin，
请求方法、cookie、CORS 全都跟着变复杂。**域名是给人看的入口，不是权限边界** ——
权限仍然由 session + `require_role` 负责。

域名来自 `.env` 的四个变量（`SITE_HOST` / `CUSTOMER_HOST` / `MERCHANT_HOST` / `RIDER_HOST`）。
**四个都留空时整个模块不生效**，三端仍按 `/customer` `/merchant` `/rider` 访问，
所以本地开发什么都不用配。

#### 装证书 / 换证书

```bash
# 把 CA 给的 *_nginx.zip 放在 ~/Downloads（或任意目录），然后：
./tools/install-tls.sh ~/Downloads
```

脚本会：本地校验证书与私钥是否配对、SAN 是否覆盖域名 → scp 到服务器 →
装进 `/etc/nginx/ssl/<域名>/{fullchain.pem,privkey.key}`（私钥 600）→
装 nginx 配置（旧配置自动备份）→ `nginx -t` 通过才 reload → 用 curl 验收三个域名。

**证书三个月一到期**（TrustAsia DV，有效期 90 天）。到期前重新申请，再跑一遍同样的命令即可，
不需要改任何代码。日期可以这样查：

```bash
echo | openssl s_client -servername customer.xllm.cloud -connect customer.xllm.cloud:443 2>/dev/null \
  | openssl x509 -noout -dates
```

⚠️ 私钥不进 Git。仓库里只有 nginx 配置（`deploy/nginx/`），证书文件全部只在服务器上。
这样做还有个副作用好处：`git clone` 下来的人拿不到私钥，也就不会不小心把站点证书用歪。

#### 为什么 cookie 不用 `Domain=.xllm.cloud`

一个会话 cookie 跨子域名共享，意味着商家在 `restaurant.` 登录会把顾客在 `customer.` 的登录顶掉 ——
三端共存演示就没法做了。现在 cookie 是主机独占的，三个域名三份会话，互不干扰；
在顾客域名打开商家页面会看到商家登录页（因为那个域名下没有商家会话），这是预期行为，
`tools/smoke_test.py` 里有一条专门验它。

## 五、部署流程

### 5.1 正常部署：一条命令

服务器上的布局是「裸仓库 + 检出工作区」：

```
/home/ubuntu/xllm.git      裸仓库（代码本体，分支 main）
/home/ubuntu/xllm          部署工作区（不是 git 仓库，由钩子检出）
├── server/                ← Flask 应用，gunicorn 的 WorkingDirectory
├── .env                   密钥（untracked，检出不会动）
└── .venv                  Python 环境（untracked，检出不会动）
```

`xllm.git/hooks/post-receive` 在收到推送后自动：检出到工作区 → 重启 `xllm.service`。

```bash
# 本地
git push server main        # 部署：检出 + 自动重启
git push origin main        # 同时更新 GitHub 存档
```

`git push server main` 的返回里应看到：

```
remote: [deploy] 已检出到 /home/ubuntu/xllm
remote: [deploy] xllm 已重启
```

> ⚠️ 钩子只检出**代码**并重启服务，**不会**重装 systemd unit。
> 若改了 `deploy/xllm.service`（比如换 WorkingDirectory），需要手动执行一次：
> ```bash
> ssh xllm 'sudo cp /home/ubuntu/xllm/deploy/xllm.service /etc/systemd/system/ \
>           && sudo systemctl daemon-reload && sudo systemctl restart xllm'
> ```

**验证：**

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://xllm.cloud/api/ping
curl -s -o /dev/null -w '%{http_code}\n' https://xllm.cloud/info/
curl -s -o /dev/null -w '%{http_code}\n' https://xllm.cloud/customer/design-system
# 三个子域名（根路径都会 302 到本端）
for h in customer restaurant delivery; do
  curl -s -o /dev/null -w "$h.xllm.cloud/ %{http_code} → %{redirect_url}\n" "https://$h.xllm.cloud/"
done
```

> ⚠️ `tools/deploy.sh` 只推**代码**。nginx 站点配置和证书不走这条路 ——
> 改它们用 `./tools/install-tls.sh`（见第三节），而且只需要在有证书/域名变动时跑。

### 5.2 ⚠️ 为什么不让服务器自己 clone GitHub

2026-10-22 实测：这台机器（腾讯云，国内）访问 GitHub 极慢甚至挂死。

```
https://github.com              200，但耗时 8.0 s（我们设的 curl 超时边界）
git clone https://github.com/... 直接挂住，120 s 无进展
```

所以服务器**不参与**和 GitHub 的同步。GitHub 仍是从本地推上去的公开存档，
但部署链路是 `本地 → SSH → 服务器裸仓库`，全程不碰外网。

**代价**：GitHub 与线上可能短暂不一致（只推了一边）。习惯上每次都推两个远端。

### 5.5 数据库结构变更（迁移 + 种子）

代码推上去只换了 Python 文件，**数据库不会跟着变**。业务表是随功能加的，
`db.create_all()` 只能建缺失的表、不会给已有表加字段，所以字段级变更走迁移脚本：

```bash
ssh xllm
cd /home/ubuntu/xllm/server
set -a; . ../.env; set +a          # ⚠️ 必须先加载 .env，否则会连到默认库
../.venv/bin/python ../tools/migrate.py
```

脚本只加不删、可重复执行，会打印每一列的处理结果（`ok` / `add`）。当前它负责：

| 表 | 补充 |
|---|---|
| `restaurants` | `cuisine` · `max_concurrent_orders` · `avg_prep_minutes` |
| `orders` | `preparing_at` · `delay_flagged_at` · `delay_reason` |
| `rider_profiles` | 整张新表（由 `db.create_all()` 建） |

首次上线或演示前需要一份数据，用种子脚本：

```bash
ssh xllm 'cd /home/ubuntu/xllm/server && set -a && . ../.env && set +a &&           ../.venv/bin/python -m shared.seed'
```

`--reset` 会 **DROP 所有表** 再重建，只在确认库里没有要保留的数据时使用。

**2026-10-22 实际执行记录（本项目上线）**：线上库在迁移前只有 M1 建的 12 张空表，
所以直接跑迁移 + 种子，没有 `--reset`：

```
tables before : 12      tables after : 13 (created: rider_profiles)
add restaurants.cuisine / max_concurrent_orders / avg_prep_minutes
add orders.preparing_at / delay_flagged_at / delay_reason / address_updated_at
seed: users 9 · restaurants 4 · menu items 32 · orders 59 · reviews 98
```

之后用真实浏览器在 `https://xllm.cloud` 上跑完了
「顾客下单 → 商家接单/备餐/出餐 → 骑手抢单/取餐/送达 → 顾客评价」全链路，
并在 1440/430 两个视口下检查了三端页面。

### 5.6 应急：rsync 直推（不进 Git 的文件）

仅用于临时排查，比如把改到一半的文件塞上去看效果。**正常流程不要用**，
否则工作区会与仓库不一致。

```bash
rsync -az --exclude='__pycache__' server/ xllm:/home/ubuntu/xllm/server/
ssh xllm 'sudo systemctl restart xllm'
```

### 🔴 红线：`rsync --delete` 不能指向工作区根目录

2026-10-22 实际踩过：对 `xllm:/home/ubuntu/xllm/` 执行 `rsync --delete`，
它把 **`.venv/` 删掉了**（`.venv` 不在本地 `server/` 里，被判为"多余文件"）。
服务当时看着还 `active`（gunicorn 进程还在内存里），一重启就 `No such file` 起不来。

恢复：

```bash
ssh xllm 'cd /home/ubuntu/xllm && rm -rf .venv && python3 -m venv .venv \
          && .venv/bin/pip install -q -r server/requirements.txt'
```

## 六、🔒 密钥管理规则

**服务器上目前有四类凭证，规则完全不同：**

| 凭证 | 放哪 | 能否进 Git | 保护方式 |
|---|---|---|---|
| 高德 **Web端** Key<br>`2c60b2cd...` | 服务器 `.env` 的 `AMAP_JS_KEY`，由 `/api/customer/config` 下发给前端 | ✅ 可公开 | 高德控制台的**域名白名单** |
| 高德 **安全密钥**<br>`59b46489...` | 服务器 `.env` 的 `AMAP_SECURITY_JS_CODE` | ✅ 可公开 | JS API 2.0 要求随页面下发 |
| 高德 **Web服务** Key<br>`1a2a76ac...` | **只能后端** | ❌ **绝对禁止** | 环境变量 |
| MySQL 密码 | 后端 `.env` | ❌ **绝对禁止** | 文件权限 600 |
| 管理大屏口令<br>`ADMIN_USER` / `ADMIN_PASSWORD` | 服务器 `.env` | ❌ **不要进 Git** | 环境变量 + 登录节流 |

> 📌 管理大屏（`/admin`）的运营账号**不在 MySQL 的 `users` 表里**，只存在于
> `.env`：默认 `ADMIN_USER=admin`，`ADMIN_PASSWORD` 未设置时回落到演示口令
> `demo1234`。演示站故意保留默认值，方便答辩时直接打开；换成真实口令后，
> 登录页上的"演示提示"会自动消失，代码不用动。详见
> [`管理大屏.md`](管理大屏.md) §二。

> 📌 实现方式：页面里**没有**硬编码 Key。地址页 / 开店页从
> `/api/customer/config` 拿 `amap_js_key` 与 `amap_security_code` 再动态加载 JS API，
> 所以换 Key 只需要改服务器 `.env` 并重启，不用改代码。
> 未配置时页面自动降级为文本地址（见 `docs/测试与验收.md` NFR-6）。

**Web端 Key 是设计上公开的**——它必然随页面下发，任何人 F12 都能看到。
所以它的安全**不靠保密，靠域名白名单**。请务必在高德控制台配好：

```
应用管理 → 我的应用 → 设置 → 域名白名单
xllm.cloud
www.xllm.cloud
127.0.0.1
localhost
```

**Web服务 Key 和数据库密码是真机密**，只能存在于服务器端：

```bash
# 建议做法：放在 ~/xllm/.env，权限 600，且 .env 已进 .gitignore
chmod 600 ~/xllm/.env
```

> ⚠️ 仓库根目录的 `.gitignore` 已经屏蔽了 `.env`、`*.pem`、`*.key`、
> `*credentials*.txt`。**提交前请再确认一遍**，密钥一旦进了 Git 历史，
> 即使后来删掉也仍然能被翻出来。

## 七、本地开发

```bash
cd server
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python app.py                      # http://127.0.0.1:8080
```

本地跑时**没有 nginx**，直接访问 Flask。由于方案 A 保留了前缀，
**本地和线上路径完全一致**：

```
https://xllm.cloud/api/ping      ← 线上
http://127.0.0.1:8080/api/ping   ← 本地
```

**本机没有 MySQL 时**，用 `DATABASE_URL` 把整条连接串换成 SQLite，
代码完全不用改（模型里主键类型已做 SQLite 变体）：

```bash
cd server
export DATABASE_URL="sqlite:///$(pwd)/dev.db"
../.venv/bin/python -m shared.seed --reset
../.venv/bin/python app.py
```

本地还需要一份 `.env`（数据库密码等）。**不要提交它**，`.gitignore` 已经屏蔽：

```bash
# server/.env
SECRET_KEY=本地随便填一个
DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=webapp
DB_USER=webapp
DB_PASSWORD=你的密码
```

Flask 不会自动读 `.env`（本项目没装 python-dotenv，保持依赖精简）。
本地开发时用 export 或者命令行前缀：

```bash
export $(grep -v '^#' .env | xargs)   # 简单粗暴地导入
python app.py
```
