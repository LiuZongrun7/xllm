# 演示脚本 · 5 分钟走完一条订单

> 目标：让评委在 5 分钟内看到**三种角色围绕同一张订单协作**，并且看清
> 「每个人只看到自己该看的信息」——这正是题目最后一句的要求。
>
> 三个端各一个域名（这样三个窗口可以同时登录，互不打扰）：
> 顾客 <https://customer.xllm.cloud> · 商家 <https://restaurant.xllm.cloud> ·
> 骑手 <https://delivery.xllm.cloud> · 官网/大屏 <https://xllm.cloud>
> 演示账号密码统一 `demo1234`

---

## 〇、演示前 3 分钟检查

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://xllm.cloud/api/ping
curl -s -o /dev/null -w '%{http_code}\n' https://xllm.cloud/api/db-ping
for h in customer restaurant delivery; do
  curl -s -o /dev/null -w "$h %{http_code}\n" "https://$h.xllm.cloud/api/ping"
done
```

| 检查 | 期望 |
|---|---|
| 官网 <https://xllm.cloud/> | 打开项目官网，三端入口都在 |
| 顾客 <https://customer.xllm.cloud/> | 跳到顾客端登录页，用 `alex` 登录 → 4 家店 + 进行中订单 |
| 商家 <https://restaurant.xllm.cloud/> | 跳到商家端登录页，用 `goldenwok` 登录 → 待接单 |
| 骑手 <https://delivery.xllm.cloud/> | 跳到骑手端登录页，用 `chen` 登录 → 可接单池 |

**三个窗口各开一个域名就行，不用无痕窗口**：三个域名的 cookie 互相独立，
同一个浏览器里可以同时登录三个账号（这正是分域名的原因之一）。

## 一、开场（20 秒）

> 这是一个外卖平台，连接顾客、餐厅、骑手三方。
> 三方围着**同一张订单**协作，但**看到的信息不一样**：
> 顾客看不到别人的地址，商家看不到别家的单，骑手只能看到待取的单。
> 权限判断全部在后端，前端隐藏按钮只是体验。

三套界面是**三套独立设计**：顾客端手机白底红按钮、商家端桌面粉白密集表格、骑手端大按钮高对比。
共享的不是像素，是状态词表、接口契约和业务规则。

---

## 二、顾客下单（90 秒）

**窗口 1 · `/customer/`（账号 `alex`）**

1. 首页：地址、菜系筛选、附近餐厅（显示距离 / 评分 / 预计时间 / 营业状态）
   - 指出 `Green Bowl Salad` 显示 **Closed**：因为它被店家手动打烊了
2. 进 `Golden Wok Kitchen`：菜单按分类分组，标注热量与库存
   - 指出 **Beef Fried Rice** 显示 *Sold out*，加不了购物车
3. 加两份菜 → 底部购物车条 → `Checkout`
4. 结算页：地址、距离校验（超出配送半径会直接拦住）、模拟支付、备注
5. `Place order` → 跳到订单进度页

> 讲：这里做了一次服务端校验 —— 餐厅是否营业、菜品是否在售、库存够不够、
> 是否达到起送价、地址是否在配送半径内。任一不过就返回**带下一步动作**的错误。

**可选（30 秒）**：同页点 `Change address`（骑手取餐前才允许），
换一个仍在配送半径内的地址 —— 距离与预计时间会重算，骑手端显示地址已变更。

**切到商家端之前**，让顾客页面停在进度页（后面回来看变化）。

---

## 三、商家接单 + 备餐（60 秒）

**窗口 2 · `/merchant/orders`（账号 `goldenwok`）**

1. 四列看板：Placed / Accepted / Preparing / Ready + On the way
2. 最左列出现刚才那单 → `Accept` → 卡片移到 Accepted
3. `Start preparing` → `Mark ready`
4. （可选）在 Preparing 列点 `Flag delay`：顾客页面立刻出现延迟横幅，预计时间 +10 分钟
5. 打开 `Menu`：改库存、切换售罄、`Restock low stock` 一键补货
6. 打开 `Settings`：营业时段、最大并发订单数（备餐产能）、平均备餐时长、配送半径
   - 把「最大并发」调小可以让顾客端显示 **Busy**，说明产能是真实参与判断的
7. 打开 `Analytics`：14 天订单/营收曲线、分时分布、Top 菜品

> 讲：状态推进只调用 `shared/order_flow.py` 里的一个函数，
> 商家端**没有**自己判断 `if status == ...` —— 三端共用同一份状态机。

---

## 四、骑手抢单 + 送达（60 秒）

**窗口 3 · `/rider/`（账号 `chen`）**

1. 顶部切到 **Online**（离线时抢不了单，会明确提示先去上线）
2. `Available` 里出现刚才那单：取餐店 → 收货地址、里程、已等待分钟
3. 点 `Grab order` → 进入 `Active`
   - 补充说明：抢单是一条 `UPDATE ... WHERE rider_id IS NULL`，用 `rowcount` 判断成败，
     **两个骑手同时点只有一个能成功**，另一个会看到 "Too late — another rider grabbed this order first"
4. 打开订单详情 → `Mark picked up`
5. 配送中点 `Share my location`（或等 20 秒自动上报）
   - 后端会拒绝精度差于 200 m、或速度超过 80 km/h 的坐标
6. `Navigate` 会打开高德地图
7. `Confirm delivered` → 页面反馈已送达，订单离开进行中列表

---

## 五、回到顾客（40 秒）

**窗口 1**：刷新订单页

- 时间轴五个节点全部变实：Placed → Accepted → Preparing → On the way → Delivered
- 出现 `Rate this order`：1–5 星评商家（可选再评骑手）
- 提交后在餐厅详情能看到评价，平均分同步变化
- 再进一次评价会提示「已经评过」—— 数据库有 `UNIQUE(order_id, target_type)` 约束

**再演示一个异常**：下一单后，在商家接单前点 `Cancel order`（可以取消并退款）；
商家开始备餐后再点，会被拦住并提示联系餐厅 —— 这就是分阶段取消。

## 六、管理大屏（40 秒）

**窗口 5**：新标签打开 `https://xllm.cloud/admin/`，用 `admin` / `demo1234` 登录。

一句话开场：**"刚才那一单，在平台运营眼里是什么样？"**

- 顶栏：`LIVE 10s` 在脉冲 —— 整块墙每 10 秒自己拉一次数据，不用刷新
- KPI 条：今天的单量 / 成交额 / 进行中 / 已送达 / 取消率 / 平均送达；`▲▼` 是与上一周期比
- 点最左侧那笔刚下的单：右侧抽屉打开，时间轴、计时、双方电话、骑手位置和金额一目了然，
  `Esc` 关掉
- 门店表：`Load 2/20` 是厨房里正在占产能的单，`Queue` 是还没被接的单，
  打烊/不在营业时段/产能满分别是 `CLOSED / CLOSED / FULL`
- 骑手表：在班状态、手里几单、平均配送时长、最后一次定位距今多久
- `Needs attention`：接单超时、出餐没人取、超过承诺时间、门店打烊还有单 —— 这些是三端都不会主动告诉你的
- 点 `7d` 看一周节奏，再点 `Today` 回到今天

收尾一句：**"大屏是只读的 —— 接单还是商家的决定，抢单还是骑手的决定。它只负责让你看见。"**

> 演示前如果数据是昨天灌的，"今天"会是空的：先跑一次
> `python -m shared.seed --reset` 再打开大屏。

## 八、可能被问到的问题

| 问题 | 回答要点 |
|---|---|
| 为什么三端长得完全不一样？ | 使用场景不同（手机消费 / 桌面后台 / 户外单手）；真实平台也是这样。共享的是状态词表、接口与业务规则，见 `docs/设计语言.md` |
| 怎么保证顾客看不到别人的订单？ | 每条查询都带归属条件（`customer_id = current_user.id`），接口有 `@require_role`，页面有 `@role_page`；越权返回 404 而不是 403，避免泄露"这单存在" |
| 两个骑手同时抢单会怎样？ | 原子 `UPDATE ... WHERE rider_id IS NULL` + `rowcount`，失败方收到 409 |
| 订单被改价/改地址会影响历史吗？ | 订单存的是快照：地址、菜名、单价都拷贝进 `orders` / `order_items` |
| 延迟怎么算？ | 时间戳链 `accepted_at → preparing_at → ready_at`，商家标记延迟会写 `delay_flagged_at` 并把预计时间顺延 |
| 地图挂了怎么办？ | 地址与距离校验不依赖地图：没有 `AMAP_JS_KEY` 时前端降级为文本地址，距离用 Haversine 在后端算 |
| 支付是真的吗？ | 模拟支付：下单即 `payment_status = 'paid'`，取消则 `refunded`，不接任何网关 |
| 大屏算第四个角色吗？ | 不算。它只读、不属于买卖任何一方，账号在 `.env` 里而不是 `users` 表，所以三端的归属查询一行都不用改（见 `docs/管理大屏.md`） |
| 大屏能改订单状态吗？ | 不能。写操作全部留在各自的端，大屏只做聚合读取，绝不绕开状态机 |

## 九、兜底方案

| 故障 | 兜底 |
|---|---|
| 现场网络不稳 | 本地跑同一套代码（`DATABASE_URL=sqlite:///...` + `shared.seed`），用 `127.0.0.1:8080` |
| 高德地图加载失败 | 页面自动降级为文本地址，不影响下单与状态流转 |
| 骑手定位授权被拒 | 用 `Share my location` 重试；定位失败不影响取餐/送达 |
| 演示数据被改乱 | 服务器上 `python -m shared.seed --reset` 重灌（会清空数据） |
