# 管理大屏 · `/admin`

一块给平台运营看的深色大屏：全平台的订单节奏、门店产能、骑手交付和异常，
**10 秒刷新一次，只读**。

代码只在这几个地方（答辩时打开这一行下面的文件就够了）：

```
server/admin/routes.py                   登录 + 聚合接口
server/admin/templates/admin/wall.html   大屏主体
server/admin/templates/admin/login.html  运营登录
server/admin/templates/admin/error.html  错误页
server/admin/static/css/admin.css        第四套设计系统（a- 前缀）
server/admin/static/js/admin.js          轮询 + 手写 SVG 图表 + 订单抽屉
```

---

## 〇、结论先行

| 问题 | 答案 |
|---|---|
| 这是"第四个角色"吗 | **不是**。运营不参与买卖，在 `users` 表里没有行，也没有任何归属于它的数据 |
| 能改订单状态吗 | **不能**。大屏是只读的，写操作全部留在各自的端 |
| 数据从哪来 | 直接读三端共用的 13 张表，**不新建表** |
| 一个人怎么登录 | `ADMIN_USER` / `ADMIN_PASSWORD` 环境变量，独立 session 键 `ops_session` |
| 刷新机制 | 前端每 10 秒拉一次 `/api/admin/overview`，可暂停、可手动刷新 |
| 和官网/三端的关系 | 入口在官网演示区，也可以直接访问 `https://xllm.cloud/admin/` |

---

## 一、它是什么，不是什么

**是**：一个观测面。把顾客端、商家端、骑手端正在发生的事拼成一块可以盯着看的墙，
回答"现在平台上发生了什么、哪里卡住了、谁需要被叫醒"。

**不是**：

- 不是第四个角色 —— 平台运营不属于市场里的任何一方，把它塞进 `users.role` 会污染
  三端所有的归属查询（`WHERE rider_id = ...`、`WHERE restaurant_id = ...`），
  还得为一个只读页面去改 MySQL 的枚举；
- 不是后台管理系统 —— 没有编辑、删除、代下单、强制取消。接单是商家的决定，
  抢单是骑手的决定，取消是顾客的权利。大屏一旦能改状态，就会变成绕开订单状态机的后门；
- 不共享三端的 CSS/JS —— 它是第四套设计系统，类名统一 `a-` 前缀。

---

## 二、为什么运营账号不在 `users` 表

`users.role` 的枚举是 `customer / restaurant / rider`，这三个值都代表"市场里的一方"，
每一行都拥有订单、菜单或配送记录。运营不属于任何一方。

所以运营凭据放在环境变量里：

```bash
# .env（服务器 /home/ubuntu/xllm/.env，权限 600）
ADMIN_USER=admin
ADMIN_PASSWORD=换成你自己的口令
```

规则：

- 没配 `ADMIN_PASSWORD` 时回落到演示口令 `demo1234`，登录页会显示一行提示；
- **一旦把 `ADMIN_PASSWORD` 改成别的值，那行提示自动消失**（`_demo_hint()` 用
  `ADMIN_PASSWORD == ADMIN_DEMO_PASSWORD` 判断）；
- 比对用 `hmac.compare_digest`，不做字符串 `==`，避免时序侧信道；
- 连错 6 次锁 5 分钟，按 `X-Real-IP`（nginx 传入）或 `remote_addr` 计数；
- 登录成功只 `session.pop("ops_session")` 再写入，**不清空整个 session** ——
  运营常在同一个浏览器里一边盯墙一边看商家端，把他踢出去只会添乱；
- 大屏的 session 键与三端的 `uid` / `role` 完全独立，登出大屏不影响三端。

> ⚠️ 节流计数存在进程内存里。gunicorn 多 worker 时每个 worker 各有一份，
> 实际容忍次数是 `6 × worker 数`。这是有意为之：这块墙的价值在于"看得见"，
> 不在于"扛得住暴力破解"，真上生产应该由 nginx 的 `limit_req` 兜底。

### 4.2 `GET /api/admin/orders/<id>`

抽屉里的单笔详情。在 `Order.to_dict(detail=True)` 之上补了三块：

- `minutes`：`to_accept` / `prep` / `to_deliver` / `total`（分钟）
- `restaurant_detail`：门店完整信息（含配送半径、产能、平均备餐）
- `rider_location` / `rider_distance_km`：骑手最后一次上报位置，以及它离门店的直线距离

订单不存在返回 `404`，不会 500。

## 五、指标口径（这块必须写死，否则数字会自相矛盾）

### 5.1 三个窗口与环比

| 窗口 | 起点 | 终点 | 环比对比段 |
|---|---|---|---|
| `today` | 今天 00:00 | 此刻 | **昨天 00:00 → 昨天同一时刻** |
| `24h` | 此刻所在整点往前 23 小时 | 此刻 | 再往前 24 小时 |
| `7d` | 6 天前的 00:00 | 此刻 | 再往前 7 天 |

`today` 的对比段刻意对齐到"昨天同一个时钟区间"，而不是"往前推同样长度"。
否则下午 1 点看大屏时，今天只和昨天 11:00–24:00 比 —— 拿今天的上午去比昨天的
午餐加晚餐，环比数字毫无意义（我们最初就踩了这个坑，`_bounds()` 里有注释）。

### 5.2 KPI

| 卡片 | 字段 | 口径 |
|---|---|---|
| Orders | `orders` | 窗口内下单数（含取消） |
| Gross value | `gross` | 窗口内**未取消**订单的 `total_amount` 之和；副标题是客单价 |
| In progress | `active` | **此刻**处于 5 种进行中状态的订单数（与窗口无关） |
| Delivered | `delivered` | 窗口内送达数；副标题是完成率 `delivered / orders` |
| Cancel rate | `cancel_rate` | 窗口内取消率；副标题是取消单数 |
| Avg delivery | `avg_delivery_minutes` | 骑手取餐 → 送达的平均分钟；副标题是商家接单 → 出餐 |

### 5.3 门店表

`LOAD` = 正在占用备餐产能的单数 / 产能（`restaurant_state()` 同一套判断），
`QUEUE` = 还没被接单的 `pending` 单数，`STATE` = `open / paused / hours / full`
四选一（与顾客端看到的"这家店现在能不能下单"完全同源）。

### 5.4 骑手表

`DONE` / `AVG TRIP` 取窗口内该骑手的已完成订单；`ON TIME` = 送达时间不晚于
`estimated_delivery_at` 的比例；`SIGNAL` = 最后一次位置上报距今多久。

### 5.5 告警规则

| kind | 严重度 | 触发条件 |
|---|---|---|
| `not_accepted` | warn / critical | `pending` 且已过 5 分钟（≥10 分钟升级） |
| `nobody_picking_up` | warn / critical | `ready` 且无骑手，等待 ≥8 分钟（≥15 分钟升级） |
| `kitchen_delayed` | warn | 商家标记了延迟（`delay_flagged_at`） |
| `past_eta` | critical | 进行中订单已超过 `estimated_delivery_at` |
| `saturated` | warn | 门店在厨房里的单数达到产能 |
| `closed_with_queue` | critical | 门店打烊但还有没被接的单 |
| `low_rating` | info | 门店评分 ≤3.4 且评价数 ≥3 |
| `rider_silent` | warn | 正在配送但位置上报停了 10 分钟 |
| `rider_offline` | warn | 不在线却手里还有单 |

按"严重度 → 等待时长"排序，最多显示 8 条。点带订单号的告警会打开抽屉。

## 六、界面

### 6.1 布局

```
┌ 顶栏：品牌 / 窗口切换 / 时钟 / LIVE / 刷新 / 全屏 / 登出 ────────────────┐
├ KPI ×6 ────────────────────────────────────────────────────────────┤
│ 需求趋势 (8)                                    │ 实时流水 (4)        │
│ ────────────────────────────────────────────────┤  （跨三行，可滚动）  │
│ 状态分布 (4)          │ 需要处理 (4)             │                    │
│ 门店产能 (8)                                     │                    │
│ 骑手舰队 (5)                          │ 热销 (7)                    │
└ 页脚：只读 · 引擎/版本/主机 · 数据量 · 更新时间 · 当前运营 ───────────┘
```

1920×1080 与 1440×900 都**不出现整页滚动**：栅格用 `fr` 分配高度，
卡片内部各自滚动。窗口 ≤1240 时改为两栏并允许页面滚动，≤900 时单栏。

### 6.2 第四套设计语言

| | 顾客端 | 商家端 | 骑手端 | **管理大屏** |
|---|---|---|---|---|
| 底色 | 白 | 粉白 | 浅灰 | 近黑 `#05080F` |
| 主色 | 番茄红 | 酒红 | 橙 | 青绿 `#3FE3BE` |
| 圆角 | 48px 胶囊 | 6px | 10px | 3px |
| 阴影 | 有 | 无 | 弱 | 无（靠描边分层） |
| 字体 | 系统无衬线 | 系统无衬线 | 加大高对比 | 系统无衬线 + **等宽数字** |
| 体感 | 让人放松 | 让人专注 | 戴手套能点 | **隔三米能读** |

细节：网格底纹（`mask-image` 做径向淡出）、`tabular-nums` 让数字不跳动、
新订单行有 1.6s 的绿色闪动、`LIVE` 圆点脉冲、`prefers-reduced-motion` 时全部关掉。

### 6.3 交互

| 操作 | 行为 |
|---|---|
| 每 10 秒 | 拉一次 `overview`；页面在后台标签页时跳过，切回来立刻补一次 |
| 点 `LIVE 10s` | 暂停/恢复轮询（暂停时变琥珀色） |
| 点刷新 | 立即拉一次，图标转 520ms |
| 点窗口 Today/24h/7d | 重新拉取，趋势图分桶跟着变 |
| 点流水行 / 告警 | 右侧抽屉打开订单详情（Esc、点遮罩、Close 都能关） |
| 全屏按钮 | 浏览器 Fullscreen API，投到第二块屏用 |
| 接口失败 | 顶栏变红显示 `Offline — retrying`，并弹一条提示；下一次成功自动恢复 |
| 401 | 直接跳登录页，不会把 JSON 糊在屏幕上 |

图表没有引入任何库：`admin.js` 里 `drawTrend()` 用原生 SVG 画柱 + 折线 + 面积，
双轴（左：订单数，右：营收），刻度用 `niceTop()` 取整到 1/1.5/2/2.5/3/4/5/6/8/10
的整数倍，鼠标移入显示当格数据。

## 九、已知边界

1. **只读**。这是设计决定，不是没做完 —— 见第一节；
2. **种子数据用相对时间**。演示前一天灌的数据，第二天大屏的"今天"就是空的，
   演示前跑一次 `python -m shared.seed --reset` 即可（会重建演示数据）；
3. **"在线骑手"依赖骑手上报**。`rider_profiles.is_online` 由骑手端切换，
   位置靠 `rider_locations`，都不做实时推送；
4. **节流是进程内存**，多 worker 时容忍度乘以 worker 数；
5. **不替代日志**。越权访问仍然只写 `[denied]` 日志（NFR-5），大屏不展示日志原文。
