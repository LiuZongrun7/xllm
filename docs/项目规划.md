## 一、项目概述

一个本地外卖平台网站，连接**顾客、餐厅、配送骑手**三方。核心不是"功能多"，而是**多个角色如何围绕同一张订单协同，并且各看各的信息**。

题目原文的关键约束（逐句拆出来的需求）：

| 题目原文 | 对应需求 |
|---|---|
| connects customers, several restaurants and delivery staff | 三种角色，多家餐厅 |
| Each restaurant controls its own opening times, menu and preparation capacity | 餐厅自主管理；营业时间/菜单/备餐能力 |
| this information may change during the day | 状态是动态的，不能写死 |
| the restaurant and a delivery member need to coordinate preparation and collection | 订单状态机：备餐 → 待取 → 配送 |
| the customer expects useful information about progress | 顾客可见的进度追踪 |
| Delays, unavailable dishes, address problems or cancellations can interrupt | **异常流程必须处理** |
| without giving everyone access to the same information | **基于角色的访问控制（题眼）** |

## 四、系统架构约定

### 4.1 API 路径约定 ✅ 已定案

**`/api` 前缀全程保留**（nginx 的 `proxy_pass` 结尾不带斜杠）。所有接口挂在
`Blueprint(url_prefix="/api/<角色>")` 上，`url_for()` 可正常工作。

```
https://xllm.cloud/api/customer/orders      ← 生产
http://127.0.0.1:8080/api/customer/orders   ← 本地（路径一致，不会搞混）
```

### 4.2 代码结构 —— 按端隔离

**目录即分工。** 答辩时每个人只需要打开自己那个文件夹：

```
server/
├── app.py                应用工厂（唯一入口，D）
├── config.py             配置（D）
├── static/css/reset.css  三端唯一共享的前端资源（就这一个文件）
│
├── shared/               D —— 共享层
│   ├── models.py         SQLAlchemy 模型（与 schema.sql 一一对应）
│   ├── extensions.py     db
│   ├── security.py       会话 + @require_role 权限装饰器
│   ├── auth.py           登录/注册/登出/验证码（三种角色共用一套凭据）✅
│   ├── health.py         /api/ping · whoami · db-ping  ✅
│   ├── mailer.py         SMTP 发信
│   └── utils.py          校验正则、统一响应
│
├── customer/             A —— 顾客端
│   ├── routes.py         页面 /customer/... + 接口 /api/customer/...
│   ├── templates/
│   └── static/css/customer.css
│
├── merchant/             B —— 商家端（结构同上，前缀 /merchant、/api/merchant）
└── rider/                C —— 骑手端（结构同上，前缀 /rider、/api/rider）
```

**为什么按端划分，而不是原来的按实体划分**（`blueprints/orders.py` 那种）：
`orders` 会被三方都碰，按实体划分会让三个人的代码挤在同一个文件里，改动互相踩。
按端划分后，A 的文件里只可能出现顾客的动作，权限归属一眼可见，git 冲突基本消失。

**唯一不能分离的四样**：`models.py`、订单状态机、`@require_role`、`reset.css`。
这四样复制成三份，等于同一个订单有三套写法，数据必然打架。

### 4.3 ⚠️ 接口契约必须先冻结

**分工是"3 个前端端 + 1 个后端"，这意味着后端是唯一的接口提供方。** 如果不先把接口定死，
会出现：三个前端画完界面全部卡住等接口，然后各自提需求，后端被三份不同的需求反复拉扯。

**所以第一步（先于任何编码）产出 `docs/API契约.md`**：路径、方法、请求体、响应体、所需角色、
错误码。冻结之后四个人才能真正并行。

### 8.1 高德地图 API（需审核）

**用途**：① 餐厅注册时在地图上标注位置；② 顾客下单时地图选点生成配送地址；③ 展示餐厅与配送位置。

**为什么适合本应用**（绑定题目需求，而非个人偏好）：

> 题目明确将 **address problems** 列为需要处理的异常情况。用户手工输入的地址存在固有歧义
> （同名道路、门牌缺失、跨区描述），是地址问题的主要来源。引入地图选点可将配送地址
> **规范化为经纬度坐标**，从源头减少该类异常；同时坐标也是**判断配送范围**与
> **展示餐厅位置**的必要输入，而这两项分别对应题目中的 *preparation capacity* 与
> *useful information about progress* 对空间信息的需求。

**技术验证已通过**：JS API 加载、地图渲染、逆地理编码、浏览器定位、Web服务 API（地理编码/距离/路径规划）全部实测可用。

**降级方案**（若未获批准）：地址改为纯文本输入 + 按行政区判断配送范围，不影响核心功能。

### 8.2 nginx + gunicorn 部署方案

**说明**：这不是应用功能层面的技术，而是**运行环境**。本项目采用 Flask 开发服务器仅用于本地调试，
生产环境使用 gunicorn 作为 WSGI 容器、nginx 作为反向代理与 TLS 终端。

**理由**：Flask 自带的开发服务器官方明确说明**不可用于生产**（单线程、无并发保护、有调试后门）。
HTTPS 是浏览器定位 API 的**硬性前提**（安全上下文要求），也是保护用户凭据的基本要求。
