## 三、五个关键设计决策

这几条是答辩最可能被追问的，先把理由写清楚。

### ① 三种角色共用一张 `users` 表

**问题**：顾客、商家、骑手都有「名称、电话、密码」，直觉上会想抽一个「父信息类」让三者继承。

**为什么不能那样做**：关系数据库**没有继承**。硬做只有两条路，都难受：

- 建一张 `info` 表存公共字段，三张角色表外键指过去 → 每次查询都要 JOIN，而且数据库无法约束"这条 info 到底属于哪张表"
- 三张表各写一遍相同字段 → 登录逻辑要写三份，密码校验散落三处

**采用方案**：一张 `users` + `role` 枚举，角色专属数据放各自的扩展表。

```sql
users       (id, role, name, phone, password_hash, ...)
restaurants (id, owner_id → users.id, ...)   -- 商家的店铺信息
-- 骑手的接单状态也放扩展字段或单独表
```

**收益**：

| | 单表 + role | 三张独立表 |
|---|---|---|
| 登录接口 | 1 个 | 3 个 |
| 权限判断 | `current_user.role == 'rider'` | 要判断 token 是哪类 |
| 密码逻辑 | 1 处 | 3 处，容易写歪 |
| 订单外键 | `customer_id` / `rider_id` 同类型 | 混合三种类型 |

### ② 订单存的是「快照」，不是「引用」

**这是整个设计里最重要的一条。**

订单是**历史凭证**——它记录的是「当时发生了什么」，不是「现在是什么」。所以有三类字段必须在订单里**冗余拷贝**一份：

| 快照字段 | 如果不冗余会怎样 |
|---|---|
| `delivery_address_text` / `lng` / `lat` | 顾客三个月后改了收货地址，**历史订单显示的送达地址跟着变** |
| `order_items.unit_price` | 商家把菜从 20 涨到 25，**上个月所有订单的金额全变了** |
| `order_items.name_snapshot` | 菜品改名或下架，**历史订单不知道该菜叫什么** |

这就是为什么 `order_items.menu_item_id` 允许为 `NULL`（菜品删除后置空），但订单依然能完整还原——**靠快照，不靠外键**。

> 答辩话术：*"订单是不可变的历史记录。凡是会被后续修改的业务数据，下单那一刻都要在订单里留一份快照，否则改一个菜价就等于篡改了所有历史订单。"*

### ③ `status` 状态机是项目的骨架

题目原文的核心考点就是这句：

> the restaurant and a delivery member need to coordinate preparation and collection, while the customer expects **useful information about progress**

"progress" 就是状态。三个端的界面全都围绕它变化：

```
pending ──→ accepted ──→ preparing ──→ ready ──→ delivering ──→ delivered
   │            │             │           │
   └────────────┴─────────────┴───────────┴──────→ cancelled
```

| 状态 | 谁能改 | 顾客看到 | 商家看到 | 骑手看到 |
|---|---|---|---|---|
| `pending` | — | 等待商家接单 | **【接单】按钮** | 不可见 |
| `accepted` | 商家 | 商家已接单 | **【开始备餐】** | 不可见 |
| `preparing` | 商家 | 备餐中 | **【备餐完成】** | 不可见 |
| `ready` | 骑手 | 等待骑手取餐 | 等待取餐 | **【接单】按钮**（可接单池） |
| `delivering` | 骑手 | 配送中 + 地图 | 已取餐 | **【确认送达】** |
| `delivered` | — | 已送达 + 评价入口 | 已完成 | 已完成 |
| `cancelled` | 视阶段 | 已取消 | 已取消 | 已取消 |

**注意 `ready` 是骑手可接单的唯一入口**——这就是题目说的"协调备餐与取餐"。

### ④ 六个时间戳 = 配送进度的数据来源

订单表上不是只有一个"时间"，而是一串：

```
created_at → accepted_at → ready_at → picked_up_at → delivered_at
                              ↘ cancelled_at
```

**它们不是装饰，是功能**：

- 顾客要的"进度信息"直接由它们推导
- **算延迟**：`ready_at - accepted_at` = 商家实际备餐耗时，和承诺时间一比就知道有没有 delay——这正是题目点名的 `delays`
- 算骑手效率、算平均配送时长

只存一个时间戳的话，上面这些全部做不了。

### ⑤ 评价用一张表 + `target_type`，而不是两张表

白板上原本是 `骑手评价` 和 `商家评价` 两张结构相同的表，还讨论了用"评价类 + 两个子类继承"。

**两张同构表 = 所有查询代码写两遍。** 合并成一张：

```sql
reviews (
  id, order_id, reviewer_id,
  target_type ENUM('restaurant','rider'),   -- 评的是谁
  target_id,                                 -- 多态指向
  rating TINYINT,                            -- 1-5 星
  content
)
```

另外两个要点：

- **`rating` 分数必须有**（原白板只有"内容"）。要做"五星骑手"、"按评分排序"，没有分数字段就无从算起。
- **`order_id` 是权限的关键**。评价必须挂在订单上，配合唯一约束：

  ```sql
  UNIQUE KEY uk_reviews_order_target (order_id, target_type)
  ```

  这保证：**只有下过这一单的顾客才能评价，且每单每方只能评一次**。这是防刷分的基础。

## 四、🔒 权限归属矩阵

**这是本设计的安全核心。** 题目最后一句是题眼：

> keeps the different participants informed **without giving everyone access to the same information**

### 铁律：权限判断必须在后端，不能靠前端隐藏

前端代码用户按 F12 就能改。真正的权限靠**每一个 SQL 查询都带上归属条件**：

```python
# ❌ 危险写法 —— 典型 IDOR（越权访问）
order = Order.query.get(order_id)
# 顾客把 URL 里的 123 改成 124，就能看到别人的订单

# ✅ 正确写法 —— 查询自带归属条件
order = Order.query.filter_by(id=order_id, customer_id=current_user.id).first_or_404()
```

### 各角色权限表

| 表 | 顾客 | 商家 | 骑手 |
|---|---|---|---|
| `users` | 读写自己 | 读写自己 | 读写自己 |
| `restaurants` | 只读（公开信息） | **读写自己的店** | 只读 |
| `opening_hours` | 只读 | **读写自己的店** | 只读 |
| `menu_items` | 只读（上架的） | **读写自己的店** | — |
| `customer_addresses` | **读写自己的** | 只读本单收货信息 | 只读本单收货信息 |
| `orders` | **读自己的**（`customer_id`） | **读自己店的**（`restaurant_id`） | 可接单池 + 自己的单 |
| `order_items` | 跟随订单 | 跟随订单 | 跟随订单 |
| `reviews` | **写自己的**（须已送达） | 只读本店的 | 只读自己的 |
| `rider_locations` | 只读本单骑手 | — | **写自己的** |
| `user_coupons` | **读写自己的** | — | — |

### 三个最容易写错的地方

1. **商家只能改状态，不能改订单金额。** 商家接口应该只暴露 `accepted → preparing → ready` 三个状态转换，不能让它改 `total_amount`。
2. **骑手的可接单池是有限视图。** `status='ready' AND rider_id IS NULL`——不能让它看到全部订单。
3. **一个订单骑手只能接一次。** 并发下两个人同时点"接单"要用数据库条件更新兜住：

   ```sql
   UPDATE orders SET rider_id=?, status='delivering'
   WHERE id=? AND rider_id IS NULL AND status='ready';
   -- 影响行数 = 0 说明被别人抢先了
   ```
